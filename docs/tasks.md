# Tasks

> REA / Architect agent: break the spec into ordered vertical slices.
> Task ID format: S<slice>-<B|M|Q>-<n>  (B = backend, M = mobile, Q = QA)
> Slice UI uses SUI-Q-n, SUI-M-0n (components), SUI-M-1nn (screen SCR-nn) and SUI-R-n; see that section.
> Each task is small enough for one agent in one sitting and has a testable definition of done.

Within a slice, tasks run in table order unless they say otherwise. Exception, Slice 1: S1-B-5 needs S1-B-3 (tokens); S1-B-6 needs S1-B-5; S1-M-3 needs S1-B-5 and S1-B-6 to pass end to end (mobile can build against mocks earlier); S1-Q-1 is the original smoke set and is done. The contract-0.2.0 follow-ups are S1-Q-2 (failing tests), then S1-B-7, and S1-M-4 (operationId rename) at any time; they are listed above S1-Q-1 only because they were added later. **Business-rule test tasks (Q) come before the backend task that implements the rule.** The Q agent writes the failing tests from `business_rules.md` test vectors; the B agent makes them pass without editing the tests. Endpoint and schema names refer to `openapi.yaml` (v0.2.0).

**Table ownership rule.** A migration is created in the slice where its first endpoint ships. Where an earlier table needs a foreign key to a later table (for example `expenses.recurring_rule_id`), the column is created early without the FK and the later migration adds the FK.

**Response fields before their data exists.** Until Slice 4 ships, every `balances`, `my_balances`, `breakdown` and `non_group_balances` field is returned as an empty array and `settled_up_since` as null (the fields are required by the schema, so they must be present).
